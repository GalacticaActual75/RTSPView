# Automatic streaming components

Starting with 1.0.46-beta.6, the Controller checks a public signed feed daily. The user does not need Python, pip, administrator approval, or the maintenance service. A full application installation is needed once to introduce this updater. Settings → Updates shows the installed dependency versions and last check.

The scheduled `Automatic streaming components` workflow lives on `main` and builds from `codex/beta`. It selects the newest published yt-dlp version (including nightly prereleases), stable Streamlink, and stable yt-dlp-ejs. It records all resolved dependency versions, bundles the pinned Deno runtime, and runs source, frozen-package, native synthetic playback, and updater tests before signing. A failed build leaves the published feed unchanged. GitHub Actions scheduling can be delayed; packages are checked daily by running hosts, not downloaded immediately on upstream publication.

The RSA-PSS SHA-256 private key is held only in the Actions secret `STREAMING_UPDATE_SIGNING_KEY`. Its public key is embedded in Infrastructure. Release assets use separate `streaming-*` prerelease tags and never replace the stable or beta application installer. `streaming-current/manifest.json` is the signed pointer; immutable timestamped packages are published first. Key replacement requires an application update that trusts the replacement key before publishing with it. Do not commit private keys.

The manifest binds package size, SHA-256, protocol, platform, dependency versions, and a monotonic release sequence. Protocol 1 packages must preserve compatibility with every application shipping protocol 1. Breaking helper changes require a new protocol and separate feed or application upgrade. The local updater bounds downloads/extraction, rejects unsafe paths and links, probes the candidate before activation, and changes the active pointer atomically. It refuses older or reused release sequences. Localhost probes exercise dependency imports, relay bytes, and the packaged JavaScript runtime without contacting a website.

Packages live under the current user's application data directory in `Streaming` (normally `%LOCALAPPDATA%\RTSPView\Streaming`; existing legacy or explicit test data directories are respected). The elevated service never loads these executables. Updates use a separate download lock, so a slow download does not prevent new streams from starting. A selection lock protects activation, rollback, and cleanup across Controller and Viewer. Each running relay holds a package lease; cleanup preserves the current package, previous package, and any leased older package. New/retrying streams use the new version while active streams retain their relay.

Startup health-check failure selects the previous or bundled helper and quarantines the failed package. HTTP 403, offline websites, and source-resolution errors do not roll back a healthy helper. Automatic dependency updates improve the speed of receiving upstream fixes; they do not guarantee access to every website or fix the currently reported YouTube refusal. Login/cookie import and DRM remain unsupported.

Validation: `dotnet run --project tests/RTSPView.StreamingUpdateChecks -c Release`, the streaming Python checks, and `tests/stream-playback.checks.py`. These use synthetic media and temporary data directories; they do not change host installation state.
